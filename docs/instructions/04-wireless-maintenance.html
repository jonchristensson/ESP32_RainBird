ESP32 Rain Sensor — Wireless Connection & Maintenance

How to reach, update, monitor, and recover the device now that it is sealed inside the Rain Bird enclosure and USB access is gone.

1

When to use this document

This is the day-to-day operations guide for the installed device. Everything here happens over WiFi — no cables, no opening the enclosure.

DocumentCoversApplies
02-flash-guide.html MicroPython firmware, first-time file upload over USB, serial verification Bench only — needs a USB data cable
03-wiring.html Boards, wiring table, converter calibration, bench tests, soldering, installation Build and install — one time
04-wireless-maintenance.html Remote access, pushing files, monitoring, recovery This one — ongoing, after install
The safety net that makes all of this low-risk: the relay is wired normally-closed, so irrigation is allowed whenever the relay is de-energized — which includes no power, no WiFi, a crashed device, a failed API call, and safe mode. Every failure mode falls back to "the lawn gets watered." The worst outcome of a mistake here is that the system waters during rain, not that it stops watering. Nothing in this document can kill your lawn.
2

One-time setup on your PC

Two tools. One you already have; the other needs downloading once.

File transfer — tools/webrepl_cli.py

Already in the project. This pushes files but cannot open an interactive prompt and cannot reboot the device — the --reboot flag shown in some WebREPL docs does not exist in this script.

Interactive prompt — the WebREPL browser client

Needed for rebooting and for running any command on the device. Clone it once:

git clone https://github.com/micropython/webrepl.git %USERPROFILE%\Tools\webrepl

Open it as a local file:

Start-Process '%USERPROFILE%\Tools\webrepl\webrepl.html'
Use the local copy, not the hosted one. The version at micropython.org is served over HTTPS, and browsers block plaintext ws:// WebSocket connections from an HTTPS page — it will appear to hang rather than give a clear error. Opening your cloned copy as a file:// URL avoids the mixed-content block entirely.
Why cloning beats downloading one file: webrepl.html is only ~1.4KB because it's a shell that loads webrepl.js, term.js (~163KB, the actual terminal emulator), webrepl.css, and FileSaver.js as siblings. Grabbing the HTML alone gives you a blank, non-functional page.

What you need on hand

  • The device's IP address on your LAN (see Section 3 if you've lost it)
  • Your OTA_PASSWORD from secrets.py — 4–9 characters, WebREPL rejects anything outside that range
3

Finding the device on your network

The IP address is your only handle on this device. With the enclosure sealed there is no serial console to ask. If your router hands out a different lease after a power cut or a router reboot, the device is still running perfectly and still logging to Google Sheets — but you cannot reach it until you find the new address.

Set a DHCP reservation — do this now

The permanent fix is to pin the address in your router so it never moves. In your router's admin page, find the DHCP or LAN settings, locate the ESP32 in the client list, and reserve its current IP against its MAC address. Espressif MACs commonly begin 24:0A:C4, 30:AE:A4, 7C:9E:BD, or A4:CF:12, which helps pick it out of a crowded list.

The exact menu name varies by router brand — look for "DHCP reservation," "static lease," "address reservation," or "MAC/IP binding" in your router's admin panel, usually under LAN or DHCP server settings. If your network uses a mesh system, the reservation is typically managed centrally by the primary router/node and holds regardless of which node the ESP32 associates with.
Binding captures whatever address the device holds at that moment — confirm it's the one you want before enabling. Afterwards, reboot the device and check it returns on the same IP; that proves the binding is doing the work rather than the device simply holding an unexpired lease.

Record the MAC address

Write it down somewhere outside this device — the MAC is the only identifier that never changes. If the IP ever moves, matching the MAC in your router's client list finds the ESP32 far faster than sweeping the subnet.

If you've already lost the address

  1. Check the router's DHCP client list first — fastest and most reliable.
  2. Confirm a candidate address is really the ESP32 by checking whether the WebREPL port answers: 
    Test-NetConnection -ComputerName <device_ip> -Port 8266
    TcpTestSucceeded : True means WebREPL is listening — that's your device.
  3. If the router is no help, sweep the subnet and then read the ARP table: 
    1..254 | ForEach-Object { Test-Connection -ComputerName ".$_" -Count 1 -Quiet -TimeoutSeconds 1 } | Out-Null
arp -a
    Adjust the subnet to match your network. Look for an Espressif MAC prefix.
The Google Sheet does not log the device's IP address, so it can't help you here. If you want that safety net, adding wlan.ifconfig()[0] to the logger payload would put the current address in every row — worth considering if you ever get locked out this way.
4

Connecting to the device

  1. Open your local webrepl.html.
  2. Change the address box from its default ws://192.168.4.1:8266 (that's the AP-mode default, not your device) to ws://<device_ip>:8266.
  3. Click Connect.
  4. At the Password: prompt, type your OTA_PASSWORD and press Enter. It does not echo — no dots, no asterisks. Type it blind.
  5. You'll see WebREPL connected.

Getting an actual prompt — press Ctrl+C

After connecting you will appear to be unable to type. This is expected and is not a browser problem.

main.py ends in an infinite while True: loop that runs the weather cycle forever. MicroPython only offers a >>> prompt once the startup script finishes, and by design yours never does. The interpreter is busy, so there is no prompt waiting for input.

  • Click once on the black terminal area so it has keyboard focus — term.js only captures keys when focused
  • Press Ctrl+C to raise KeyboardInterrupt, break out of the main loop, and land at >>>
Ctrl+C stops the main loop. While you sit at the prompt there are no weather checks, no logging, and no WiFi watchdog. The relay holds its last state — de-energized, so irrigation is allowed. Nothing is at risk, but you will see a gap in the Google Sheet for as long as you stay there, and the device will sit idle indefinitely until you reboot it. Don't wander off and leave it parked.
WebREPL accepts one client at a time. While your browser session holds the port, every tools/webrepl_cli.py push will fail. Disconnect the browser before pushing files, and reconnect afterwards. Nearly every confusing "the push isn't working" moment is this.
5

Pushing a file to the device

The full rhythm for every change. Run from the project root.

  1. Disconnect the browser — single client only.
  2. Push the file: 
    python tools/webrepl_cli.py -p <OTA_PASSWORD> weather.py <device_ip>:weather.py
    The destination filename is given explicitly, so a typo silently creates a new file rather than replacing the one you meant. Keep both sides identical unless you have a reason not to.
  3. Reconnect the browser, click the terminal, press Ctrl+C.
  4. Reboot so the new file is imported: 
    import machine; machine.reset()
    The terminal drops its connection immediately — that's the reset working, not an error.
  5. Reconnect and verify (Section 6).
Pushing a file does not apply it. Modules are imported once at boot and stay resident. Until you reboot, the device keeps running the old code — including the old config.py values. A push with no reboot is a no-op from the device's point of view.

Pushing several files

Repeat the push command for each file, then reboot once at the end. Don't reboot between pushes — a device running a half-updated set of files can fail in confusing ways.

A file with a syntax error will boot-loop the device. If main.py or anything it imports fails to parse, the device crashes on boot and resets repeatedly. This is recoverable — it's exactly what safe mode exists for (Section 8) — but confirm your change at least runs locally before pushing, and prefer pushing one file at a time so you know what broke.
6

Verifying a change took effect

You can't easily diff files on the device, so verify by observing behaviour instead. Two ways.

Read the value back at the prompt

Fastest confirmation that a config change landed. After rebooting, Ctrl+C to a prompt and import the module:

import config
config.RAIN_THRESHOLD_6H

If it prints the old value, the push didn't take or you rebooted before pushing.

Reading a value this way re-imports the module from flash, so it reflects what's actually stored — but remember you've just stopped the main loop to do it. Reboot again when you're done looking.

Watch the Google Sheet

The boot weather check runs immediately on startup, so a new boot row should appear within a minute or two of any reboot. That row alone confirms the device came back up, connected to WiFi, reached the weather API, and reached Google. For behavioural changes, the decision, api_success, or free_memory columns will show the effect.

Monitoring — reading the Google Sheet

With no LED visible and no serial console, the Sheet is your entire window into the device. These baselines come from measured field data, not estimates.

ColumnHealthyInvestigate when
event check every ~15 minutes Repeated boot rows — the device is resetting. Several within a minute means a boot loop.
Row interval 15m05s–15m10s, very consistent Gaps over 20 minutes — missed cycles from WiFi drops, API failures, or resets
api_success TRUE Sustained FALSE. Isolated blips are normal network noise.
wifi_rssi −57 to −66, averaging about −60 Consistently below −70, or a downward trend — antenna or interference issue
free_memory 95,872–98,944 when API calls succeed A floor that walks steadily downward across many cycles — that's a leak
decision allowed, or blocked with a matching block_reason blocked with no rain in the readings, or the reverse
Free memory oscillates — that's normal. Readings snap to discrete levels roughly 2,048 bytes apart, because whether a 2KB allocation block is held at sampling time depends on gc.collect() timing. A ~3KB swing with no trend is healthy. Judge by whether the floor declines over many cycles, not by cycle-to-cycle variation.
When API calls are failing, expect a lower band. Measured over 41 consecutive failing cycles, free memory sat at 87,600–93,936 — about 5KB below the healthy band, with wider swings. This is a bounded plateau, not a leak: the failure path's gc.collect() runs while the exception is still propagating, so the traceback briefly pins more memory. It is stable indefinitely, so a long outage will not exhaust the heap.
Not every boot row is a crash. WIFI_WATCHDOG_TIMEOUT_S is 300, so if WiFi stays down for five minutes the device deliberately reboots itself to recover. An isolated boot row preceded by a gap in the log is very likely this — a router reboot or a brief outage — not a firmware fault. What should worry you is boot rows clustered seconds apart, or boot rows with no preceding gap at all.
A device that has stopped logging entirely is not necessarily broken. Check whether you left it at a Ctrl+C prompt — that stops the main loop and therefore all logging, and is by far the most common cause of an unexplained gap.
8

Safe mode — what it is and how to get out

Safe mode exists so a bad push can be repaired over WiFi instead of requiring the enclosure to be opened. It's the reason a broken file is an inconvenience rather than a disaster.

How it triggers

A counter in RTC memory tracks resets. Three resets less than 60 seconds apart trips it. A gap longer than 60 seconds, or a full power cut (which clears RTC memory), resets the count — so ordinary reboots never trigger it.

What the device does in safe mode

  • Prints a banner: === SAFE MODE: N rapid resets, cause=… — awaiting OTA repair ===
  • De-energizes the relay, so irrigation runs normally the whole time
  • Blinks the LED on a slow 2-second pattern (not visible once installed)
  • Attempts WiFi once, and starts WebREPL if it connects
  • Idles forever — no weather checks, no logging, no watchdog reboot

Recognizing it

The Sheet goes completely silent — safe mode never runs a weather cycle. If WebREPL still connects, the banner is your confirmation.

Repairing from safe mode

  1. Disconnect the browser, push the corrected file with tools/webrepl_cli.py as usual.
  2. Wait at least 60 seconds before rebooting.
  3. Reconnect and reboot with import machine; machine.reset().
The 60-second wait is not optional. Safe mode is an infinite loop, so a reset is the only way out — but resetting immediately counts as another rapid reset and drops you straight back in. Letting more than 60 seconds elapse makes the stored timestamp stale, so the next boot is treated as normal.
If WiFi doesn't connect in safe mode, WebREPL never starts and the device is unreachable until you cut power at the Rain Bird. Safe mode deliberately does not retry WiFi — it attempts once and then idles.
After any full power cut, safe mode needs four rapid resets rather than three. The reset check runs before NTP synchronizes the clock, so the first post-power-on timestamp is written against an unsynced clock. Once NTP jumps the time forward by ~26 years, the next comparison sees an enormous gap and treats that reset as unrelated, absorbing one from the count. This only ever makes safe mode harder to trigger, never easier.
9

Common maintenance tasks

Changing rain thresholds

The most likely routine change — seasonal tuning, or reacting to a summer where the lawn is drying out. Edit config.py locally, push it, reboot.

  • RAIN_THRESHOLD_6H — inches of rain in the past 6 hours that blocks irrigation (default 0.25)
  • RAIN_THRESHOLD_12H — inches forecast over the next 12 hours that blocks irrigation (default 0.5)

Lower values block more aggressively (less watering); higher values block less often (more watering).

To force a block for testing, use a negative value like -1.0, not 0.0. The comparison is a strict >, and on a dry day the reading is exactly 0.000, so a 0.0 threshold will not reliably trigger. Always restore the real value afterwards.

Changing WiFi credentials — read this before touching your router

Changing your router's SSID or password before updating the device will lock you out permanently. The device cannot connect, so WebREPL never starts, so you cannot push the new credentials — and the only recovery is opening the enclosure and connecting USB, which the permanent wiring makes impractical. Order matters absolutely here.

The safe order:

  1. Edit secrets.py locally with the new credentials.
  2. Push it to the device while the old network is still up and the device is still reachable.
  3. Confirm the push succeeded — no errors from tools/webrepl_cli.py.
  4. Now change the router.
  5. The device loses its connection, reconnects on the new network, and resumes. Watch for a fresh row in the Sheet to confirm.
If the new network hands out a different IP, you'll need Section 3 to find it again. Set the DHCP reservation on the new network too.

Routine health check

No connection needed — just open the Sheet.

  • Rows still arriving every ~15 minutes
  • api_success mostly TRUE
  • wifi_rssi still around −60
  • free_memory floor not trending downward
  • No unexplained boot rows

When something goes wrong — recovery ladder

Work down this list. Each rung costs more than the one above it, so don't skip ahead.

Rung 1 — Check the Sheet before touching anything
Are rows still arriving? If yes, the device is healthy and the problem is your connection, not the device. If they stopped, note the exact time of the last row — that tells you when things went wrong and often why.
Rung 2 — Reconnect WebREPL
Confirm the IP still answers on port 8266 (Section 3). If it connects, Ctrl+C to a prompt and reboot. If you'd left it parked at a prompt earlier, this alone fixes the silence.
Rung 3 — Look for the safe-mode banner
Silent Sheet plus a working WebREPL connection strongly suggests safe mode. Push the corrected file, wait 60+ seconds, reboot (Section 8).
Rung 4 — Power cycle at the Rain Bird
If WebREPL won't connect at all, cut power at the controller's breaker or transformer, wait a few seconds, restore. This clears RTC memory, so the reset counter starts fresh and the device takes a clean boot. Irrigation is unaffected while the device is down — the relay fails open.
Rung 5 — Open the enclosure, connect USB
Last resort, and awkward by design since the wiring is permanent. From here you're back to 02-flash-guide.html — serial console, mpremote, and a full re-upload if needed. Reaching this rung means WiFi itself is broken (wrong credentials pushed, router changed first, or dead antenna).
Throughout all of this, irrigation keeps running. Every failure state — crashed, unreachable, safe mode, powered off — leaves the relay de-energized and the sensor circuit closed, which the Rain Bird reads as "no rain detected, water normally." You have time to fix things properly rather than in a hurry.
